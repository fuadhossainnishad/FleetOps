# Initial API contract (conceptual)

No HTTP dependency, controller, authentication flow, or API exists in the repository. Paths below are proposals for the first useful vertical slice, not implemented contracts. Exact identifiers, payload fields, API versioning, and error envelope should be settled before implementation.

| Method / path | Purpose and request / response | Validation, access, status, concurrency |
|---|---|---|
| `POST /api/v1/shipments` | Create a shipment. Request carries only customer-authorized execution instructions; response returns shipment ID, current status, and creation time. | Authenticated customer; server derives customer ID from identity, never trusts it from body. Validate required instruction fields. `201`, `400`, `401/403`, `409` for account/state conflict, `503` if persistence unavailable. Idempotency key recommended for retry-safe creation; persist key and result only when this endpoint is implemented. |
| `GET /api/v1/shipments/{shipmentId}` | Read shipment detail and current lifecycle/assignment summary. | Customer owner or operations role; scope check in query/application path prevents IDOR. `200`, `401/403`, `404` (avoid revealing other tenant existence), `503`. No mutation/idempotency. |
| `GET /api/v1/shipments` | Customer-scoped shipment list; operations may use an explicitly authorized operational filter. | Cursor pagination, bounded page size, stable `createdAt, shipmentId` ordering. Validate filters and reject unsupported sort fields. `200`, `400`, `401/403`. Do not expose unrestricted cross-customer listing. |
| `POST /api/v1/shipments/{shipmentId}/dispatches` | Assign a chosen vehicle and driver. Request includes their IDs and, if policy requires, an idempotency key. Response includes dispatch ID and assignment state. | Operations dispatcher role plus resource-scope check. Validate lifecycle, eligibility, and uniqueness inside transaction. `201`, `400`, `401/403`, `404`, `409` for stale state/resource conflict, `503`. Idempotent replay should return same result; key scope and retention need policy. Concurrent conflict does not partially assign. |
| `POST /api/v1/dispatches/{dispatchId}/release` | Release an assignment, returning resources and shipment to the allowed state. | Operations role; release reason only if policy mandates it. `200`, `400`, `401/403`, `404`, `409`, `503`. Idempotency key useful for retried command; duplicate release returns accepted current outcome or conflict by chosen contract. |
| `POST /api/v1/shipments/{shipmentId}/completion` | Record delivery completion. Request evidence is intentionally unspecified pending proof-of-delivery requirements; response gives terminal status and completion identity/time. | Operations/assigned driver according to authorization decision. Validate active assignment and required proof. `200` or `201` (choose once resource semantics settled), `400`, `401/403`, `404`, `409`, `503`. Idempotent command required for unreliable client retries. |

No endpoint is proposed for arbitrary status PATCH, CRUD of every resource, GPS writes, or fleet management. Tracking ingestion needs source authentication, rate/volume limits, source identity and deduplication semantics first. Tracking reads need audience and freshness requirements before a route is selected. Persistence entities must not serialize directly as request/response bodies.

Expected API concurrency behavior is explicit `409 Conflict` for a command based on state that has changed, with no partial effects. A version/ETag can be added for customer edits if a mutable shipment-edit workflow is approved; do not add generic optimistic HTTP concurrency preemptively.
